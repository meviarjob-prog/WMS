# План: модуль транспортной логистики (отложено до завершения WMS)

Статус: **не начато**. Сначала доводим до готовности основную WMS, затем
приступаем к этому модулю. Документ фиксирует все решения и открытые
вопросы, обсуждённые до паузы, чтобы не терять контекст между сессиями.

## Идея

Отдельное направление бизнеса: компания забирает короба у
селлеров-клиентов, свозит на логистический склад, компонует по
направлениям в паллеты и отправляет получателям. Нужна возможность
проследить каждый короб через все этапы цепочки — по аналогии с тем, как
в WMS уже отслеживается путь короба через приёмку/размещение/перемещение.

## Архитектурное решение: не отдельный сервис, а новые blueprint'ы в этом же приложении

Причины:
- короба, которые забирает водитель, физически становятся теми же
  WMS-коробами после приёмки на логскладе — одна БД проще, чем синхронизация
  по API между двумя приложениями;
- склад приёма ("лог склад") — это просто ещё один `Warehouse`, ничего
  изобретать не надо;
- авторизация/роли уже есть в WMS — добавляется ещё несколько ролей.

Единственное принципиально новое: **публичная самостоятельная регистрация
клиента** — сейчас в WMS аккаунты создаёт только админ. Нужен отдельный
маршрут регистрации без логина, создающий пользователя с ролью `client`,
без доступа ни к чему из внутренней WMS.

## Роли

- `client` (селлер) — самостоятельная регистрация. Видит только свои
  заявки, форму подачи новой заявки, трекинг своих коробов.
- `logist` (оператор-диспетчер) — новая роль. Очередь заявок, формирование
  рейсов, назначение водителей, загрузка машин.
- `driver` (водитель) — новая роль, мобильный интерфейс: задания на
  сегодня, сканирование коробов на каждом этапе.
- `admin` — как сейчас, плюс управление машинами/тарифами/пользователями.
- Кладовщик хаба — вероятно, существующая роль `warehouse` (сортировка по
  направлениям похожа на уже имеющиеся «Размещение»/«Инвентаризация»).

## Сущности (черновой набор моделей)

- **Client** — карточка компании-селлера (название, ИНН, адрес забора по
  умолчанию, контакты), привязана к `User` с ролью client.
- **Vehicle** — машина: госномер, тип, вместимость в коробах
  (`capacity_boxes` — вместимость считаем количеством коробов, не
  объёмом/весом, по потребности v1).
- **Driver** — привязан к `User` (role=driver), опционально закреплён за
  машиной.
- **PickupRequest** (заявка) — client_id, адрес и время, заявленное
  кол-во коробов (`declared_box_count`), **`delivery_type`**:
  `pickup` (забор машиной) или `self_delivery` (клиент везёт сам),
  статус, ссылки на рейс(ы).
- **VehicleRun** (рейс) — vehicle_id, driver_id, дата, статус, список
  заявок, остаток вместимости.
- **PickupAssignment** — связка заявка↔рейс с фактическим количеством
  коробов именно в этом рейсе. Нужна отдельной сущностью (не просто FK на
  заявке), потому что одна большая заявка может быть разбита на **два**
  рейса/машины.
- **TransportBox** — не дублирует `Box`, а привязывает к существующей
  записи `Box` транспортную карточку: текущий этап цепочки, к какому
  рейсу/паллете относится сейчас.
- **Pallet** — паллета сборки по направлению: направление, список коробов,
  статус. (Открытый вопрос: направления — те же города-склады
  маркетплейсов из `Warehouse.marketplace_city`, или отдельный справочник
  именно транспортной компании — см. ниже.)
- **BoxStatusEvent** — история (append-only, не перезаписывается): box_id,
  этап, время, кто отсканировал, в рамках чего (рейс/паллета/склад),
  **+ геометка (lat/lon)**, см. раздел про геолокацию. Это и есть механизм
  «проследить любой этап».
- **TariffTier** — тариф: `leg` (`pickup`/`delivery`), `min_qty`,
  `max_qty` (null = без верхней границы), `price_per_box`. Единый
  расчётный механизм для обеих сторон (см. раздел про тарифы).
- **MonthlyStatement / BillingEntry** — ежемесячный акт сверки по клиенту:
  список поставок за месяц, по каждой — заявлено/факт коробов и
  применённый тариф, сумма, признак расхождения.

## Жизненный цикл короба (статусная модель)

1. Заявка подана.
2. Задание выдано водителю (либо, для `self_delivery`, этот шаг
   пропускается).
3. Забор товара (сканирование при заборе) / либо прибытие клиента с
   самопривозом.
4. В пути на лог. склад.
5. Прибытие и разгрузка на складе.
6. Сборка по направлениям / упаковка в паллеты.
7. Паллета в пути к направлению.
8. Разгрузка в пункте назначения.
9. Выгружен / доставлен.

Каждый переход — новая строка `BoxStatusEvent`. Страница трекинга (и для
клиента, и для внутреннего пользователя) — хронологический список событий
по конкретному коробу.

## Самопривоз клиентом

Отдельный `delivery_type = self_delivery`:
- не нужен `VehicleRun`/водитель;
- цепочка короче: «заявка подана» → сразу «прибытие на склад» (кладовщик
  сканирует по факту приезда клиента) → дальше как обычно;
- **не платный этап** (клиент не пользовался забором) — в биллинг по
  забору такие заявки не попадают, только по доставке (если применимо).

## Вместимость машины и алгоритм подсказки

- Вместимость — количество коробов на тип машины (`capacity_boxes`).
- При формировании рейса: остаток = вместимость − уже назначено. Если
  остаток > 0 — система подсвечивает подходящие необработанные заявки и
  предлагает добавить в этот же рейс.
- Если заявка больше остатка вместимости — разбивается на несколько
  `PickupAssignment`: часть в этот рейс, остаток — в новый рейс (та же
  машина вторым рейсом или другая машина), алгоритм подбора для остатка
  запускается заново (рекурсивно тот же механизм).

## Тарифы и ежемесячная сверка

Раз услуги платные, тарифицируем **по факту, не по заявке** — расхождение
заявлено/факт разбирается как в WMS для перемещений (`receive_with_discrepancy`
— тот же паттерн: не блокирует, помечается отдельно).

**Доставка до конечной точки — решено:**
- тарификация по коробам, ступенчато по объёму;
- пример: ≤10 коробов — 500 ₽/короб, >10 — 420 ₽/короб;
- **вся партия по одной ставке целиком** (не маржинально/по нарастающей):
  12 коробов = 12 × 420 = 5040 ₽, а не 10×500 + 2×420;
- **порог сравнивается с объёмом ОДНОЙ поставки/партии**, не суммарно за
  месяц по клиенту. Если клиент отправляет 3 партии по 4 короба за месяц —
  каждая по 500 (порог 10 ни разу не превышен), даже если итог за месяц 12.

Общая формула: `сумма = qty_в_партии × price_per_box(qty_в_партии)`, где
`price_per_box` берётся из `TariffTier` по количеству коробов именно этой
партии.

**Забор (pickup) — открытый вопрос**, ещё не решено: тарифицируется так
же по объёму партии (та же тиерная модель), фиксированной ставкой
независимо от объёма, или зависит от расстояния до клиента (адрес забора)?
Расчётный механизм (`TariffTier`) уже спроектирован достаточно гибко для
объёмного варианта; если потребуется расстояние — нужно будет либо
привязывать тариф к паре точка-забора↔хаб, либо добавлять отдельный тип
тарифа `distance_based`.

Итоговый акт сверки за месяц по клиенту: список поставок → по каждой
кол-во коробов (заявлено/факт) и применённый тариф → сумма за забор (если
платный) + сумма за доставку → итог, с выгрузкой в Excel по образцу уже
существующих отчётов в WMS.

## Геолокация

Два уровня, решение — делать первый сразу, второй отложить:

1. **Геометка на событии (делаем сразу, дёшево)** — при нажатии водителем
   «Забрал»/«Прибыл на склад» браузер один раз берёт координаты
   (Geolocation API), пишутся в `BoxStatusEvent` (доп. поля lat/lon).
   Даёт подтверждение места события — полезно и для споров при сверке, и
   для проверки самопривоза (что скан реально произошёл на складе).
2. **Живое отслеживание машины на карте (в бэклог, не для v1)** —
   постоянная трансляция координат водителя, отдельный канал обновления
   (веб-сокет/поллинг), карта на фронте. Ощутимо более тяжёлая история,
   не вписывается в текущую синхронную request/response архитектуру без
   отдельного проектирования. Не блокирует основной цикл заявка → забор →
   склад → сборка → доставка, поэтому переносится на потом.

## Экраны по ролям (черновой список)

- **Клиент**: регистрация → «Подать заявку» (адрес, кол-во коробов, тип
  забор/самопривоз, желаемое время) → «Мои заявки» со статусом и
  трекингом каждого короба → ежемесячный акт сверки.
- **Оператор-логист**: очередь новых заявок → конструктор рейса (машина,
  водитель, список заявок с индикатором заполненности и подсказкой «можно
  добавить ещё N коробов») → список рейсов в работе.
- **Водитель** (мобильный, по аналогии с уже готовыми сканирующими
  экранами в WMS): задания на сегодня → сканирование при заборе (+
  геометка) → отметка «выехал»/«прибыл на склад».
- **Хаб/склад** (роль `warehouse`, как и в WMS): приём коробов от рейса →
  сборка в паллеты по направлениям (в духе уже существующего «сканировать
  короб в короб» — только «сканировать короб в паллету») → отправка
  паллеты → отметка выгрузки в точке назначения.
- **Трекинг**: доступен клиенту по своим коробам и внутренним ролям по
  любому — ввели номер короба/заявки, видно полную хронологию этапов.

## Порядок реализации (по фазам, каждая — отдельные коммиты с тестами)

1. Модели + регистрация клиента + подача заявки (включая самопривоз) +
   очередь заявок у оператора (без вместимости — ручное назначение).
2. Машины/водители + расчёт вместимости + подсказка «есть место» +
   разбиение заявки на несколько рейсов.
3. Мобильный поток водителя: сканирование при заборе (+ геометка),
   привязка коробов к рейсу, прибытие на склад.
4. Сборка в паллеты по направлениям на складе, отправка, разгрузка.
5. Трекинг-страница (полная история) + видимость для клиента.
6. Тарифы и ежемесячный акт сверки (после того как ясен тариф на забор).

## Открытые вопросы (остались после паузы)

1. Короб заводится в WMS заранее (клиент сам создаёт номенклатуру/короб
   до подачи заявки) или создаётся на месте при заборе/самопривозе?
2. Направления паллет — те же города-склады маркетплейсов
   (`Warehouse.marketplace_city`), что уже есть в WMS, или отдельный
   справочник направлений именно транспортной компании?
3. Регистрация клиента — с модерацией/подтверждением оператором перед
   первым использованием, или сразу активный аккаунт?
4. **Тариф на забор (pickup)** — та же объёмная тиерная модель, что и у
   доставки, фиксированная ставка независимо от объёма, или зависит от
   расстояния/адреса клиента?
5. Расхождение факт/заявка при сверке — блокирует закрытие месяца или
   просто помечается для ручного разбора (пока предполагается второе, по
   аналогии с движением в WMS)?
